# Cross-runtime production benchmark (evidence-driven)

This is how the team distinguishes a **model limitation** from missing tools, poorly activated skills, a weak specification or ineffective independent review. Do not declare a winner based on one model producing an attractive static screenshot or code that compiles.

## Repeatable benchmark task

After the project has a live disposable Studio test place, give each candidate runtime/model the **same approved, small vertical slice** (for example one interactable mining rock, server-authoritative reward, real inventory count UI, coherent approved rock asset family, hit/collect feedback and phone + desktop controls). Use the same versioned `QUALITY_BRIEF.md`, art bible, source asset/reference licenses, tool permissions, runtime-capability contract, complete skill lock and acceptance scenarios. Record version and whether actual skill files were read, not just discovered.

Run three documented trials as useful: (A) the same model without the Studio bridge to measure handoff limits (planning-only, never production-approved); (B) verified Studio bridge and normal required skills; (C) the same full runtime with an art/UX specialist split and independent visual/gameplay review. Do not conflate tool-availability differences with intelligence differences. Only run external generation where source/license/cost policy permits.

## Collect before comparing

- Exact runtime/model version, reasoning configuration, skill lock/hash and model routing date, agent isolation/proof of task handoff, tool failures, Studio bridge/screenshot/view capability.
- Repeatable CLI checks and real Studio acceptance steps with operator, commit, test place, device, console logs; server security and reconnect/retry cases.
- Art-direction approval, in-game views at actual camera distance, a functional UI state/interaction trace, actual asset manifest and evidence that final placeholders were either removed or deliberately approved as art style.
- Fresh independent visual, technical and gameplay reviewers; separate human observation notes for actual playability and visual cohesion. Log failure reasons and cost/time only when measured.

## Decision

Classify each failed gate as TOOL_UNAVAILABLE, SKILL_NOT_LOADED, SPEC_UNCLEAR, INTEGRATION_FAIL, FUNCTIONAL_FAIL, ART_QUALITY_FAIL, UI_FAIL or REVIEW_FALSE_POSITIVE. Improve the responsible skill/role/tool contract before blaming the base model. Try an alternative model tier only after controlling the other variables; keep previous runtime valid until a replacement actually passes your own representative benchmark. Never manufacture a performance score or claim that this benchmark has run before real Studio evidence exists.
